    Quickstart¶

    This page gives ordinary developers three executable journeys: discovering capabilities and generating a new project, adopting an existing project, and querying one requirement during daily work. Each journey includes exact commands; architecture routing and API details live in the linked references.

    Shared Installation Prerequisite¶

    For local candidate validation, build the three 0.14.0 tarballs from the Foundation workspace and install them into a temporary consumer. Run these commands from the Foundation workspace root:

    pack_dir="$(mktemp -d)"
(cd packages/skill-family-contracts && pnpm pack --pack-destination "$pack_dir")
(cd packages/skill-family-harness-node && pnpm pack --pack-destination "$pack_dir")
(cd packages/skill-family-engineering-kit && pnpm pack --pack-destination "$pack_dir")
mkdir "$pack_dir/consumer" && (cd "$pack_dir/consumer" && npm init -y)
(cd "$pack_dir/consumer" && npm install "$pack_dir/skill-family-contracts-0.14.0.tgz" "$pack_dir/skill-family-harness-node-0.14.0.tgz" "$pack_dir/skill-family-engineering-kit-0.14.0.tgz")

    After publication, install the exact coordinate skill-family-engineering-kit@0.14.0, then run the npm exec commands below.

    New Project: Discover Capabilities and Generate a Skeleton¶

    Start by evaluating the project's uses, then select stable capabilities explicitly. --list-capabilities is read-only; the --uses file should contain problems, constraints, retained guarantees, and optional filters, never credentials or private business data.

    npm exec -- skill-family-kit adopt-plan --list-capabilities --all --scope all --locale en --uses ./uses.json
npm exec -- skill-family-kit scaffold --root ./my-project --project-id my-project --capability foundation.contracts.object-validation --capability foundation.harness.atomic-write
npm exec -- skill-family-kit check --root ./my-project

    supportedMatches is candidate discovery only, and needsDecision means that the project still has to confirm the use. The command does not write a Profile or claim adoption. A successful scaffold means that the skeleton and contract-test wiring were written; the adapter, domain guarantee, and consumer tests remain to be completed.

    Existing Project: Adopt and Complete Migration¶

    Run read-only adopt-plan first, then record uses and one of the four decision dispositions in the migration manifest. Only direct-adoption and compatibility-layer may target a Foundation capability; keep-business and foundation-gap stay with the consumer.

    npm exec -- skill-family-kit adopt-plan --root ./existing-repo
npm exec -- skill-family-kit adopt-plan --root ./existing-repo --list-capabilities --all --scope all --locale en --uses ./uses.json
npm exec -- skill-family-kit check --root ./existing-repo

    adopt-plan writes no files and does not migrate automatically. Migration state complete means that the Profile, managed files, legacy exit, checks, and four evidence classes are all satisfied; it does not mean contract integration is complete. The consumer's adapter tests and domain gate must state that conclusion.

    Daily Work: Query One Requirement¶

    When the capability ID is unknown, use a deterministic substring query in the intended language. An empty result is no-text-match; a result containing only unsupported capabilities is boundary-found. Neither result creates a foundation-gap decision.

    npm exec -- skill-family-kit adopt-plan --list-capabilities --locale en --filter "must not leave a partial file when a write fails"

    To establish real-host qualification, provide a complete request, bindings, and --native to the explicit qualification sub-action:

    npm exec -- skill-family-kit check qualification \
  --root <consumer-repo> \
  --capability foundation.kit.plugin-verification \
  --request <request-json> \
  --bindings <private-bindings-json> \
  --native

    The real qualification claim comes only from one explicit, bounded host execution. Candidate discovery, migration complete, and contract integration do not replace it.

    Legacy Short Path: Generate a Skeleton¶

    If the project has already confirmed that a uses assessment is unnecessary, it can still generate a compliant skeleton directly.

    npm exec -- skill-family-kit scaffold --root ./my-project --project-id my-project
npm exec -- skill-family-kit check --root ./my-project

    The commands above first generate a skeleton, then run engineering diagnostics on the generated result. scaffold writes only to an empty target directory; a non-empty or conflicting target is refused and not touched; check diagnoses only, it does not fix. Verification passes when check exits with code 0.

    Existing Project: Read-Only Inventory (Compatibility Entry)¶

    The goal is to first see whether the existing repository can be adopted, without changing any bytes.

    npm exec -- skill-family-kit adopt-plan --root ./existing-repo
npm exec -- skill-family-kit check --root ./existing-repo

    adopt-plan outputs the current state, target Profile, exact write set, conflicts, and the legacy-implementation exit list, with zero change to the input repository's bytes. check performs read-only diagnostics only. Decide whether to perform a write after confirming the inventory results.

    Architecture Designer: Decide Ownership¶

    The goal is to determine which Foundation layer an architecture requirement should land in, or whether it should stay with the consumer.

    1. Read the eight-step decision order in docs/agents/architecture-routing.md.
    2. In docs/agents/capability-catalog.json, find the capability by layer and intent, and read its entrypoints, sideEffects, failureSemantics, ownedByCaller.
    3. When publishing, task lifecycle, or artifact relationships are involved, route to release-skill, loop-agent, and artifact-graph respectively.

    The hard boundary of routing: Foundation does not own remote writes, business state machines, model orchestration, or domain-audit semantics. Capabilities that fall into keep-business or foundation-gap do not forcibly expand Foundation.
